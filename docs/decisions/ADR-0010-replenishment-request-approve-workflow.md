# ADR-0010: Replenishment becomes a request → approve → confirm workflow

**Status:** Accepted
**Date:** 2026-07-31

## Context

Until now, a replenishment was a single Finance-side action: `POST /replenishments` (permission `allocation.record`, held by `FINANCE_OFFICER`/`FINANCE_MANAGER`/`SUPER_ADMIN`) directly created an issued `Replenishment` row, gated only by BR-013's three-month check evaluated at that same moment (`replenishments.rules.ts`'s `evaluateThreeMonthCompliance`, called from `ReplenishmentsService.createReplenishment`). The unit then confirmed hand-to-hand receipt via the locked, exact-match flow (ADR-0009).

This deliberately redesigns the first half of that flow, following the same treatment already given to cash-count and month-close this session: a real workflow change from what `docs/MASTER_SRS.md` §8.5 previously described, documented here rather than silently reinterpreted. The unit itself now initiates a replenishment request; Finance reviews and approves or rejects; only on approval does a `Replenishment` row get created, using the existing confirm step unchanged.

**Scope note on BR-001/repository rule 2** ("no approval workflow... no pending state," BR-001/FR-EXP-008): that rule governs pre-spend approval of *expense vouchers* — a unit spending cash it already holds, where saving the entry must remain sufficient with no gate in front of it. This ADR concerns *replenishment of the unit's cash from Finance*, the opposite transaction direction, and does not touch expense recording — saving an expense voucher still requires no approval, ever, unchanged. BR-013's own text already implies a check-and-decide step (a hold with an audited exception); this ADR relocates where that step happens, it does not invent approval where none existed.

## Decision

1. **The unit's own assigned user submits a replenishment request** — amount and reason only, nothing else. Every petty-cash-enabled unit has exactly one assigned `UNIT_USER` today (confirmed against `prisma/seed-data.ts`'s `DEMO_USERS`); the request permission is also granted to `UNIT_INCHARGE`, which stays wired into the permission map even though no demo user currently holds it, consistent with how `allocation.confirm_receipt` is already granted to both roles.
2. **BR-013 is enforced at submission, not at Finance's review** — a non-compliant unit cannot submit a request at all; nothing is persisted. The target period is the real current Asia/Karachi month (`currentKarachiPeriod()`, the same anchor `GET /compliance/:unitId`'s `nextReplenishment` already uses), not a client-supplied date — a request has no `issueDate` of its own until Finance supplies one at approval.
3. **Finance Manager or Super Admin reviews a cross-unit pending queue** (`GET /replenishment-requests/pending`) and either:
   - **Approves** (`POST /replenishment-requests/:id/approve`), supplying `issueDate`/`referenceNo`/`paymentMode`/`remarks` — the fields the old direct-create form used to collect, now moved to this step. The amount is never editable here; it is always the request's own amount, read server-side. Approving creates the real `Replenishment` row via `ReplenishmentsRepository.create` (reused, not duplicated).
   - **Rejects** (`POST /replenishment-requests/:id/reject`), supplying a mandatory `rejectionReason`. No `Replenishment` row is ever created for a rejected request.
4. **A Finance-initiated override path preserves BR-013's audited-exception clause** (`POST /replenishment-requests/override`), gated by the existing `compliance.override_three_month_hold` permission (unchanged scope: `FINANCE_MANAGER`/`SUPER_ADMIN`). It creates the request already `APPROVED` and its `Replenishment` row in the same atomic step, mirroring exactly what the old single-actor direct-create-with-exception did — just relocated to a dedicated route. It requires a non-empty `exceptionReason` and re-checks compliance server-side, rejecting with 400 if the unit turns out to already be compliant (forcing the normal request/approve path instead). This is the *only* way a held unit gets a replenishment; the unit itself has no bypass at all.
5. **The old direct-create endpoint (`POST /replenishments`) is removed entirely.** The only ways a `Replenishment` row is created going forward are approval of a request or the override path. `POST /replenishments/:id/confirm` and `GET /replenishments/pending/:unitId` are untouched — still the exact ADR-0009 locked, exact-match confirm flow.
6. **New permission keys**: `replenishment.request` (`UNIT_USER`, `UNIT_INCHARGE`) and `replenishment.approve` (`FINANCE_MANAGER`, `SUPER_ADMIN` — deliberately excluding `FINANCE_OFFICER`, which previously held `allocation.record` and could create replenishments directly). Approving is a heavier, one-shot financial commitment than the old shared `allocation.record` capability, so it's scoped to match `compliance.override_three_month_hold`'s existing roles rather than `allocation.record`'s wider set. This is a real narrowing of Finance Officer's capability, flagged and confirmed before implementation, not an incidental side effect.

## Schema

`Replenishment` gains exactly one new nullable column, `requestId` (unique, FK to the new table) — its shape is otherwise byte-for-byte unchanged, so nothing reading it (contracts, the confirm flow, reports) needed to change. All new state lives in a new `ReplenishmentRequest` table: `status` (`PENDING`/`APPROVED`/`REJECTED` — a real enum, following `MonthlyClosingStatus`'s precedent for a genuine multi-state field, unlike the nullable-timestamp-pair pattern `Replenishment`'s own create-then-confirm step uses), a BR-013 compliance snapshot (`isCompliant`/`exceptionReason`/`exceptionBy`/`exceptionAt`, mirroring `Replenishment`'s own now-legacy fields), decision fields (`decidedBy`/`decidedAt`/`rejectionReason`), and the Finance-supplied disbursement fields (`issueDate`/`referenceNo`/`paymentMode`/`remarks`) that move from create-time to approve/override-time. `DELETE` is revoked on the new table, extending the append-only convention already applied to `monthly_closings`/`replenishments` (rule 9/17).

## Rationale

Modeling this as a new, separate request table — rather than adding a status field directly onto `Replenishment` — keeps the existing, well-tested create-then-confirm shape of `Replenishment` completely stable. Every existing reader of that table (the confirm flow, reports, the ledger-posting path) needed zero changes. The alternative (folding request/approve state onto `Replenishment` itself) would have meant a wider migration and more surface area for the untouched confirm flow to regress.

## Consequences

- `docs/MASTER_SRS.md` §8.5 rewritten to the 6-step flow above; Appendix A and the §6.3 RACI summary gain rows for submit/approve, both marked ADR-0010.
- Existing integration coverage for the old direct-create endpoint and its BR-013/exception/duplicate-reference/idempotency behavior moved to `replenishment-requests.integration.spec.ts` against the new endpoints; `replenishments.integration.spec.ts` now only covers the compliance timeline read and confirming receipt, using the override path for fixture setup (the equivalent single-step atomic creation).
- BR-013's target period tying to "now" (rather than a client-supplied date) means test isolation for compliance scenarios can no longer use a synthetic future-dated year block the way the old suite did — `replenishment-requests.integration.spec.ts` instead uses two dedicated units untouched by any other integration file's fixtures, one with its real preceding three months idempotently force-closed in `beforeAll`.
- Finance Officer can no longer originate a replenishment in any form (previously via `allocation.record`) — this is intentional (see Decision §6), but is a real, user-facing capability change for that role, not just an implementation detail.
- There is no limit on how many `PENDING` requests a single unit may have open at once; a unit can submit several requests before Finance decides on any of them. This was not flagged as a requirement and is not enforced — worth revisiting if it turns out to be a real operational problem.
